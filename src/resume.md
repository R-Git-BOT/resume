# プロジェクト経験

## 1. メタバース型オンラインゲーム／新規ミニゲームのサーバーサイド開発

### 期間

2023年12月～2024年12月（約13か月）

### プロジェクト経験概要

アバターを利用して仮想空間内で交流し、複数のアトラクションを遊べるメタバース型ソーシャルオンラインゲームの開発に参画しました。

担当したのは、最大8人が同一ルームで遊ぶ正体隠匿型ミニゲームです。19種類の役職、役職ごとのスキル、投票・再投票、1対1のカードバトル、PvEエネミー、16種類の状態異常、イベント、切断・再接続、リマッチなど、多数のゲーム要素を持つリアルタイムゲームでした。

### チーム情報

- プロジェクト人数：6～7名
- バックエンドエンジニア：1～2名
- Unityクライアントエンジニア：3名
- プランナー：1名
- デザイナー：1名
- 役割：サーバーサイドエンジニア
- 担当工程：詳細設計、API設計、DB・マスタ設計、実装、E2Eテスト、不具合修正、コードレビュー、運用改修

Unityクライアントからの通信受信、サーバー上でのゲーム状態更新、DBへの永続化、クライアントへのレスポンス・イベント配信まで、サーバーサイド領域を初期開発からリリース後の運用改修まで一貫して担当しました。

### 開発・実装内容A：ゲーム進行・役職スキル処理

#### 概要

Unityクライアントからプレイヤー操作を受け取り、サーバー上でゲーム状態を更新して各クライアントへ配信するリアルタイムゲーム処理を担当しました。

#### どのような機能の開発・実装か

- 19種類の役職と役職固有スキル
- プレイヤーステータスと16種類の状態異常
- ダメージ・回復・死亡判定
- 投票、再投票、特殊投票
- 1対1のカードバトル
- PvEエネミー、アイテム、ゲーム内イベント
- マッチング、ルーム作成、報酬付与API
- 役職、スキル、マップ、敵、イベント等のマスターデータ

対象機能では、HTTP API 29本、クライアント・サーバー間のgRPCメッセージ92本、サーバー内部メッセージ94本が使用されていました。

#### 課題・問題点

役職、スキル、状態異常、ゲームシーンの組み合わせが多く、複数操作が同時に発生した際に、処理順序の競合や状態不整合が起きやすい構造でした。

また、ゲームループ内で例外が発生すると、そのルームに参加している最大8人全員のゲーム進行が停止する可能性がありました。役職情報や占い結果など、本人以外へ送信してはいけない情報の配信制御も必要でした。

#### Action

- 私がC#でゲームロジック、状態管理、Web API、通信メッセージを実装しました。
- 競合が発生していた処理をBehavior単位の逐次実行へ変更しました。個別にロックを追加するのではなく、60fpsゲームループのFIFOキュー上で直列に処理し、処理順序を保証しました。
- ゲームループ内の例外送出を見直し、想定可能な異常系ではエラーログを記録したうえで処理を継続する方式へ変更しました。
- 役職情報や占い結果などの秘匿情報は、ユーザーIDを含む個別宛先へ配信し、不要なクライアントへデータ自体が届かないようにしました。
- 役職、スキル効果値、制限時間、ドロップ率などをマスターデータ化し、コード変更なしで調整できる構成としました。

#### 使用した技術

- C#／.NET 8：ゲームロジック、状態管理、Web APIの実装
- ASP.NET Core：マッチング、ゲーム作成、接続認証、報酬付与API
- MagicOnion：UnityクライアントとのgRPC双方向通信
- NATS：通信サーバーとゲームループサーバー間のメッセージ連携
- LogicLooper：60fpsゲームループとゲーム状態の更新
- MessagePack／AES：通信データのシリアライズと暗号化
- MySQL／Dapper：プレイヤー情報、ゲーム結果、マスターデータの取得・更新
- Ridgepole：役職、スキル、敵、イベント等のDBスキーマ管理

#### 成果

- 初期実装からリリース後の運用改修まで約1年間一貫して担当しました。
- 競合による状態不整合と、例外によるルーム停止のリスクを抑えました。
- 複雑な役職・スキル構成を持つリアルタイムゲームの安定化に対応しました。
- Web API、ゲームロジック、通信プロトコルの関連リポジトリで、約1,300コミットを実施しました。

### 開発・実装内容B：切断・再接続・ルームライフサイクル

#### 概要

ゲーム中の通信切断、再接続、再入場、ゲーム復帰、リマッチ、ルーム終了処理を担当しました。

#### どのような機能の開発・実装か

- 切断後のプレイヤー状態保持
- 再接続時の認証、ルーム再参加、状態復元
- 復帰時のスポーン位置・同期対象の復元
- 全員退出時の終了処理
- 準備タイムアウト、ルーム有効期限
- 全員同意によるリマッチ
- ゲーム終了後のサーバーリソース解放

#### 課題・問題点

1回の操作がUnity、MagicOnion、NATS、60fpsゲームループを横断するため、不具合の発生箇所を特定しにくい構成でした。

ゲーム中の状態は主にオンメモリで保持されており、事後調査ではサーバーログと通信履歴が主な手掛かりでした。切断後にユーザーが同期対象へ残る、再入場時の位置がずれる、リマッチ後に復帰できないなどの不具合が発生していました。

#### Action

- 私がサーバーログ、NATSメッセージ、MagicOnionの送受信内容、Unity上の挙動を時系列で照合しました。
- 接続認証、ルーム参加、同期リスト登録、スポーン処理、セッション破棄の各段階に分けて原因を切り分けました。
- 準備タイムアウト、ルーム有効期限、全員退出時の終了、リマッチ成立条件など、ルームのライフサイクル処理を実装・修正しました。
- ゲーム中の状態をDBへ保存しない構成を補うため、配役、死亡、勝敗、プレイヤー行動等の分析・調査用ログを実装しました。

#### 使用した技術

- MagicOnion：クライアント接続、切断、再接続の管理
- NATS：ルーム単位・ユーザー単位の内部メッセージ配信
- LogicLooper：ルーム状態、プレイヤー状態のオンメモリ管理
- Redis：接続トークン、接続先情報の管理
- JWT／Refit：サーバー間の入室権限受け渡し
- Azure Data Explorer：障害調査用ログ、行動分析ログ

#### 成果

- 再戦後の復帰不能、切断後の状態残留、スポーン位置の不整合などを修正しました。
- 離脱者や放置ユーザーが存在する場合にも、ルームを終了してリソースを解放できる状態へ改善しました。
- リリース後に発生した切断・再接続関連の問題を継続的に修正し、安定運用に貢献しました。

### 開発・実装内容C：E2Eテスト基盤

#### 概要

実サーバーへ複数のテストクライアントを接続し、マッチングからゲーム終了・リマッチまでを検証するE2Eテストを整備しました。

#### どのような機能の開発・実装か

最大8クライアントを同時接続し、マッチング、入室、役職配布、投票、スキル使用、ゲーム終了、リマッチまでを自動実行するテストクライアントを作成しました。

#### 課題・問題点

ユニットテストが十分に整備されておらず、実DB、実ゲームループ、実gRPC通信を使用するE2Eテストが主な品質担保手段でした。

非同期メッセージの到着を固定時間のsleepで待つ方式では、実行環境によってテストが不安定になりやすい問題がありました。

#### Action

- 私が約6,000行、40超のテストメソッドからなるテストクライアントを整備しました。
- 固定時間待機ではなく、特定のプロトコル受信または期待する状態が成立するまで待機する条件待ち処理を実装しました。
- 役職や参加人数に応じた複数パターンを検証できるようにし、不具合修正時には再現ケースを追加しました。

#### 使用した技術

- C#：テストクライアント、検証ロジックの実装
- MagicOnion：実サーバーへの複数クライアント接続
- MessagePack：実際の通信プロトコルを用いた検証
- MySQL：テスト用ゲームデータ、マスターデータ
- Docker／Docker Compose：テスト対象となるローカル環境の構築

#### 成果

- マッチングからリマッチまでの主要フローを、実環境に近い構成で継続的に確認できるようにしました。
- ユニットテストが十分でない環境において、リグレッション検知と複雑なゲーム状態の品質担保に活用しました。

## 2. バーチャルイベントプラットフォームのサーバーサイド開発

### 期間

2022年6月～2023年11月（約1年6か月）

### プロジェクト経験概要

スマートフォン、PC、VR端末からバーチャル空間のイベントへ参加できる、メタバース型バーチャルイベントプラットフォームの開発に参画しました。

一般ユーザーはアバターでイベントへ参加し、チャット、ボイスチャット、動画・PDF等のコンテンツ閲覧、チケット・アイテム購入を行います。イベント主催者は専用サイトからイベント、エリア、チケット、出展物を管理し、運営担当者は管理ツールからマスターデータ、アプリバージョン、ログ、商品情報等を管理します。

汎用プラットフォームに加え、外部ECや企業向けID基盤と連携する個別プロダクトの開発にも携わりました。

### チーム情報

- プロジェクト人数：約20名
- 4社による混成開発チーム
- 役割：サーバーサイドエンジニア
- 担当工程：詳細設計、API設計、DB設計、実装、テスト、不具合修正、コードレビュー対応、リリース対応

一般ユーザー向けAPI、イベント主催者向けサイト、運営管理ツール、一部C++リアルタイムサーバーの設計・実装・テスト・不具合修正を担当しました。

### 開発・実装内容A：外部ID認証・アカウント連携

#### 概要

外部ID基盤を利用したログイン機能と、既存のゲストアカウントへ外部IDを連携する機能を担当しました。

#### どのような機能の開発・実装か

- アプリ内WebViewから外部認証画面への遷移
- 認証完了後のコールバック処理
- JWT検証
- 新規アカウント作成
- 既存アカウントへのログイン
- ゲストアカウントへの外部ID連携
- 外部サービス向け所持チケット集約API

#### 課題・問題点

アプリ、WebView、自社API、外部認証基盤をまたぐ多段の認証フローであり、認証開始時のリクエストとコールバック結果の対応関係を保証する必要がありました。

また、ゲストアカウントから本アカウントへ移行する際に、アカウント状態や認証情報の有効期限が正しく更新されない不具合がありました。

#### Action

- 私がPHPで認証開始、コールバック、ログイン、アカウント連携用のAPIを実装しました。
- 認証開始時に生成したstateや一時情報をRedisへ保存し、コールバック時に照合することで認証リクエストの対応関係を検証しました。
- 外部認証基盤から受け取ったJWTについて、署名、issuer、audienceを検証しました。
- ゲストアカウント連携時の状態遷移を確認し、アカウント区分や認証情報の更新処理を修正しました。

#### 使用した技術

- PHP 7.4：認証API、アカウント作成・連携処理の実装
- Redis：stateや認証途中の一時情報の保存
- Azure AD B2C：外部ID認証基盤
- JWT：署名、issuer、audienceの検証
- MySQL：アカウント情報、外部ID連携情報の永続化

#### 成果

- 外部IDによる新規登録、ログイン、ゲストアカウント連携を本番環境へリリースしました。
- 複数サービスをまたぐ認証フローについて、不正なコールバックや状態不整合を防止できる構成としました。

### 開発・実装内容B：外部ECサービス連携

#### 概要

外部ECサービスへのシングルサインオン、商品情報取得、注文Webhook受信、購入アイテム同期を担当しました。

#### どのような機能の開発・実装か

- アプリから外部ECサイトへのログイン状態引き継ぎ
- 商品・コレクション情報の取得
- 注文・支払い・商品作成Webhookの受信
- 購入結果に応じたアプリ内アイテム付与
- 商品管理テーブルと運営管理画面

#### 課題・問題点

外部ECサービスからのWebhookが届かない場合、購入済みの商品がアプリ内へ反映されない可能性がありました。

また、同一コードベース上で複数プロダクトを運用しており、商品設定や購入ログが別プロダクトと混在しないようにする必要がありました。

#### Action

- 私が外部ECサービスへのSSO URL生成、商品取得、注文Webhook受信、アイテム同期処理を実装しました。
- Webhookだけに依存せず、管理者が後から手動で購入情報を再同期できる処理を追加しました。
- 購入ログをプロダクト別のテーブルに分離し、開発環境と本番環境の設定値をデータ側で切り替えられるようにしました。
- 複数箇所に存在していた外部EC連携処理を共通クラスへ集約し、重複コードを削減しました。

#### 使用した技術

- PHP 7.4：SSO、Webhook、商品・注文同期処理の実装
- Shopify Multipass：外部ECへのシングルサインオン
- Shopify GraphQL Admin API：商品・コレクション情報の取得
- Webhook：注文、支払い、商品作成イベントの受信
- MySQL：商品設定、購入履歴、アイテム付与情報の管理
- Ridgepole：新規テーブルのスキーマ管理

#### 成果

- 外部ECサービスとの連携機能を本番環境へリリースしました。
- Webhookが欠落した場合にも購入情報を復旧できる運用経路を用意し、外部サービスとの連携失敗によるデータ不整合へ対応できるようにしました。
